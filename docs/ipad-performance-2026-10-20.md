# iPad 문서 열기·썸네일·페이지 추가 성능 조사

실행 경로는 `BandalApp → NativeWorkspaceView → NativePDFWorkspaceModel → NativePDFHost`다. 사용하지 않는 React 화면은 변경하지 않았다. 이 기록은 앞선 [자료·올가미·공유 개선](ipad-interaction-improvements.md)에 이어 진행한 성능 작업이다.

## 재현과 원인

실기기 백업의 읽기 전용 사본에서 PDF 22개를 익명 fixture로 추출했다. 원본 백업은 수정하지 않았고 사용자 문서·필기는 저장소에 추가하지 않았다. 성능 재현용 문서는 6쪽, 필기 7,094개, 전달 JSON 약 53.7MB다. 준비용 데이터 입력은 시간 측정에서 제외하고 실제 `NativePDFWorkspaceModel.attach/layout`부터 로딩 완료, `addPage`부터 새 페이지의 로딩·저장 완료까지 측정했다.

- 문서 열기: 검증한 JSON을 초기 스냅샷에서 다시 직렬화하고 복사했다. PDFKit이 미리 만든 화면 밖 페이지까지 경로와 Metal 메시를 동기 계산했다.
- 페이지 추가: PDFKit의 전체 재인코딩이 원래의 색상 공간·폰트·투명도·이미지 설정을 바꾸어 보존 검증에서 `CONFLICT`가 발생했다. 기존 필기 행을 모두 삭제·재삽입했고, 다시 열 때 목적지로 이동하기 전에 첫 페이지 필기를 준비했다.
- 썸네일: 같은 요청의 중복 작업, 화면에서 사라진 요청, 메인 스레드의 필기 합성, 불필요한 원본 바인딩·복사가 있었다.
- 자료 목록: 초기화 조건이 뒤집혀 내용이 그대로인 정기 새로 고침에서도 전체 색인을 다시 썼다. 공유 목적지 목록도 파일까지 조사했다.
- 편집·여러 창: 지우기·개체 변경·실행 취소 뒤 전체 필기를 재조회했고, 한 개체 변경을 다른 창에 보낼 때도 모든 필기 payload를 깊게 비교했다.
- Markdown: 이미지 파일 읽기·디코딩과 가져올 파일의 base64 변환이 메인 스레드에서 실행됐고 이미지 하나가 도착해도 편집기 전체를 다시 구성했다.

## 변경

초기 스냅샷의 중복 인코딩을 제거했다. 불변 JSON 검증은 유지하고, 비교가 필요한 행만 정규화한 바이트를 만든다. 필기 경로와 메시 준비는 실제 viewport에 들어오는 페이지로 한정한다. 저장된 위치 복구는 최초 레이아웃과 합쳐 목적지에 도착한 뒤 잉크를 준비하며, 그 뒤 로딩 완료를 표시한다.

페이지 추가는 원본 객체 그래프를 유지하고 페이지 트리만 바꾸는 제한된 writer를 먼저 사용한다. 지원하지 않는 구조는 기존 보존 검증 경로로 돌린다. 본문·리소스·렌더링 설정이 같은 구조임을 입증할 수 있는 페이지만 픽셀 렌더링 검사를 생략한다. 주석 appearance, 텍스트, geometry, 링크, 책갈피, 문서 정보 검증은 유지한다. 기존 필기의 페이지·내용·시각이 그대로면 DB 쓰기를 하지 않는다. 저장 저널과 페이지 변경 전후 복구 자료는 유지한다.

페이지 실행 취소 가능 여부는 필요한 이전/이후 기록 한쪽만 읽는다. 이미 JSON 문자열인 DB 열을 다시 전체 직렬화하지 않고 정확한 문자열·스칼라 값으로 비교한다. 같은 7,094행의 별도 macOS 측정에서 194–270ms가 24–26ms로 줄었다. 숫자/Boolean, 부호 있는 0, Unicode 조합 표기, 행 순서 차이를 구분하는 검사는 유지한다.

페이지 파일 저장이 끝난 뒤 위치 저장이나 새 화면 열기에 실패한 경우에는 확정된 변경 결과를 보관한다. 재시도는 실패한 후처리부터 이어가며 페이지를 다시 추가하거나 이전 revision의 화면을 저장 장벽에 다시 넣지 않는다. 실제 임시 SQLite 오류를 주입해 위치 저장 실패와 새 revision 채택 후 필기 로딩 실패를 각각 검증한다.

썸네일 요청은 공유하고 취소하며, PDFKit 문서와 필기 합성은 제한된 작업 큐에서 처리한다. 캐시 적중은 DB 조회와 JSON 해시보다 먼저 처리한다. 편집 뒤 캐시 무효화는 해당 문서에 한정한다. 자료 색인은 변경되지 않았으면 쓰지 않고, 공유 목적지 갱신은 폴더만 읽으며 내용이 같으면 공유 파일을 다시 쓰지 않는다.

개체 편집은 영향받은 ID만 다시 읽는다. 생성 시간이 같은 행은 해당 페이지의 정렬을 재확인해 쌓임 순서를 유지한다. 여러 창의 변경 ID 힌트는 같은 coordinator 기준을 공유하는 경우에만 사용하며, 새 창·독립 재조회·아직 전파하지 않은 변경은 전체 비교로 돌아간다.

전체 회귀에서 초기 목록을 읽지 않은 세션의 부분 조회가 다른 창의 개체를 표시 목록에서 빠뜨리는 문제가 발견됐다. DB 원본은 남아 있었지만 undo/redo 표시도 불완전해졌다. 최초 편집 전에 전체 canonical 목록이 확보됐는지 별도로 확인하도록 고쳤다. 이미 초기 로딩을 완료한 정상 편집 경로의 부분 조회는 유지한다.

Markdown 이미지와 미디어 읽기는 작업 큐로 옮겼다. 이미지 완료는 현재 attachment만 갱신하며, 취소·문서 교체·한글 조합 중에는 오래된 결과가 커서와 실행 취소를 훼손하지 않도록 검사한다.

## 측정 해석

시뮬레이터의 동일 사본 측정이다. 실기기 지연으로 환산하지 않는다. 최초 작업 전 앱 전체를 측정한 수치는 없으며, 전체 열기·페이지 추가의 비교 기준은 이번 작업 도중 구간 계측을 넣은 시점이다.

| 측정 범위 | 비교 전 | 개선 후 |
|---|---:|---:|
| 실제 Workspace 열기, 7,094개 필기 준비 완료까지 | 6,042.7ms | 4,116.9ms |
| 페이지 추가, 저장·다시 열기·목적지 준비 완료까지 | 9,571.9ms | 5,113.8ms |
| 7,094행 초기 스냅샷 구성 | 1,999.8ms | 391.8ms |
| 두 창 사이 한 개체 변경 비교 | 684.6ms | 2.31ms |
| 1,695행 썸네일 기존 메인 스레드 합성 / 새 작업 큐 첫 생성 | 2,441.8ms | 859.4ms |
| 썸네일 캐시 적중 20회 평균 | — | 0.001ms |

최신 같은 문서 실행에서도 스냅샷 구성은 378.5ms였다. 전체 열기와 페이지 추가는 초기 layout·위치 복구를 합친 스냅샷에서 측정했다. 원시 집계는 [performance-measurements.json](ipad-interaction-improvements/performance-measurements.json)에 남겼다.

첫 페이지 자체의 복잡한 필기 경로·메시 생성과 전체 필기 읽기 비용은 남아 있다. 편집 복구의 디스크 동기화와 외부 변경 전 저장 장벽은 성능을 이유로 제거하지 않았다. 한글 입력 중 Markdown의 복구 파일 동기 저장도 내구성 정책을 유지했다.

## 원본 보존 검증

추가 전 실패하던 4개를 포함해 실제 PDF 22개 모두 페이지 추가에 성공했다. 실패했던 4개 문서의 기존 71쪽은 픽셀, 검색 가능한 텍스트, 주석을 포함한 렌더링 결과를 전수 비교해 동일했다. 이는 해당 사본에 대한 검증이며 모든 종류의 PDF를 지원한다는 주장은 아니다. 서명·암호화·지원하지 않는 문서 기능의 제한은 유지한다.

개별 계측은 `BANDAL_PRIVATE_PDF_REPLAY_DIRECTORY`를 명시한 Debug 테스트에서만 집계 숫자로 출력한다. 문서 이름·경로·본문은 기록하지 않는다. 회귀 및 최종 설치 결과는 아래에 기록한다.

## 최종 회귀·UI 검증

| 실행 | 전체 | 통과 | 건너뜀 | 실패 |
|---|---:|---:|---:|---:|
| 최초 전체 회귀 | 698 | 691 | 6 | 1 |
| 초기 canonical 목록 처리 수정 후 관련 회귀 | 78 | 77 | 1 | 0 |
| 최종 시뮬레이터 UI | 3 | 3 | 0 | 0 |

최초 전체 회귀의 실패는 `NativePDFRepositoryTests.testStableTextboxCreationTokenSurvivesFailureAndDoesNotAdoptIdenticalPeerObject` 한 테스트에서 발생한 assertion 15개다. 앞서 설명한 초기 목록 누락을 수정한 뒤 기존 테스트의 기대값을 바꾸지 않고 통과했다. 재검증은 Persistence·Repository·Host·페이지 변경 복구·Workspace 저장 장벽을 포함한 관련 78개 테스트이며, 전체 698개를 다시 실행한 결과는 아니다. 건너뛴 1개는 별도의 개인 문서 fixture를 요구하는 테스트다.

최종 UI 테스트는 실제 Photos 앱의 공유 화면에서 반달을 선택하고 과목·폴더를 지정해 가져온 뒤 재시작하는 흐름, 자료 보기 방식의 유지와 자료 트레이 접근, 올가미 자동 스크롤로 다른 페이지에 필기를 이동하고 실행 취소·재시작 후 저장을 확인하는 흐름을 모두 통과했다. 결과 묶음은 각각 `.build/performance-regressions.xcresult`, `.build/performance-recovery-final.xcresult`, `.build/performance-ui-final.xcresult`다.

## 실제 iPad 업데이트와 보존 확인

2026-10-20 02:04 KST에 iPad Pro 11형 3세대(iPadOS 26.5)의 `1.0.0(4)`를 **Release `1.0.0(5)`**로 업데이트했다. 앱과 공유 확장 모두 유효한 서명과 `group.app.bandal.ipad` 권한을 가지며, 두 프로비저닝 프로필에 실제 기기가 포함된다. 테스트 인자 없이 실행했고 마지막 백업 비교 후 다시 실행해 프로세스를 확인했다.

앱을 종료한 상태에서 설치 전후 Documents·Preferences·ShareInbox를 각각 새 디렉터리로 복사했다. 자료 파일 **66개 전부**의 경로와 바이트 해시가 같았다. 두 SQLite 데이터베이스의 무결성 검사를 통과했고 PDF 필기 **12,291행**, 생성 영수증 12,291행, 변경 영수증 55행, 화이트보드 개체 **43행**의 모든 기존 열 값을 보존했다. 검사는 임시 DB와 WAL 사본만 열어 백업 원본을 수정하지 않았다.

기존 설정 28개 중 26개가 같고 삭제된 설정은 없다. 변경된 두 항목은 StoreKit 확인 시각과 새 앱 컨테이너에 대한 PDF 설정 이전 경로 등록이다. App Group의 과목 2개·하위 폴더 0개 목적지 목록도 그대로 읽힌다. 공유 전체 UI 흐름은 시뮬레이터 검증이며, 실제 기기의 카카오톡/Photos 공유 조작이나 성능 수치를 측정한 것으로 해석하지 않는다.
